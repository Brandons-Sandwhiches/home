# Zoom maps

## What it is

Five zoom levels. The script saves levels 2 and 3 as files. The agent builds level 4 on demand.

| Zoom | Looks at | Code | Markdown | Plain text, media |
| --- | --- | --- | --- | --- |
| 1 Earth | all projects | `work/dashboard.html` (in v1) | same | same |
| 2 10,000 ft | one project | `AGENTS.md` points at `.agents/map.md`: each folder, one line | same | same |
| 3 1,000 ft | one folder | file, then function and class names | `wiki/index.md`: page, one line (in v1) | file, one line |
| 4 100 ft | one file | outline with line numbers | headings with line numbers | `rg -n` or first lines |
| 5 1 ft | the lines | read lines 40 to 80 | read the section | read the range |

- Generated by one small script on `universal-ctags` (Python, JS/TS, C++ and Markdown headings; Windows, Mac, Linux). Rebuilt in the pre-commit hook so it cannot go stale.
- Every map starts with: what it covers, when the script built it, and "not listed does not mean missing, search".
- Tags stay for markdown topics that cut across pages (lesson, decision). Code needs none; function names are its tags.
- Caps: project map 150 lines. A bigger repo gets one map per top folder, and the root map lists only folders.
- AGENTS.md line: "Read the map first. The map says what exists, not what is inside; read the lines before you answer."

## How it compares

| Option | Good at | Weak at | Cost and fit for home |
| --- | --- | --- | --- |
| **Zoom maps (this)** | Exact names, always current, plain files every tool reads, nothing to run | Finds by name, not by meaning ("where do we handle retries?") | Free. One script. Works the same in Claude Code, Codex, opencode |
| **Embeddings / vector index** (what Cursor and Continue do inside their apps) | Meaning-based search | Goes stale, needs a service or database, hard to share across tools, can miss exact names | Extra thing to run and trust. Only worth it on repos too big to map |
| **Code-intelligence servers** (Serena, Sourcegraph/SCIP) | Exact "who calls this" and "go to definition" across a whole repo | Setup, a server per language, heavy for small projects | Good second step. Serena runs locally as an MCP server, so it stays tool-neutral. Catalog it separately |
| **Packers** (Repomix, code2prompt) | One file to paste a whole repo into a chat | Dumps everything, burns the context window | Fine for one-off pastes, wrong for daily agent work |
| **Hosted tools** (Sourcegraph Cody, Greptile, Augment, DeepWiki-style generated wikis) | No setup, strong search on big repos | Your code leaves the machine, vendor lock-in, a monthly bill, and some work in one app only | Doesn't fit "client spaces never cross" or the tool-neutral rule without a per-project check |
| **Agent search alone** (grep, glob) | Already built in, zero setup | Wastes reads on big repos; does not know what it hasn't looked at | Baseline. The maps give it a starting point instead of replacing it |

Details above come from general knowledge of these tools, not a fresh test of each. Re-check before relying on one.

## Recommendation

1. Start with zoom maps. Cheapest, and files in git are the only form every tool shares.
2. Add Serena (or similar) only when a repo has real call-graph questions.
3. Skip embeddings and hosted tools until maps plus search measurably fail.

## How to decide it works

Add a golden task to the eval set: "find where X lives" or "which page covers Y". Run it with and without the map, 3 runs each. Compare tokens and files opened. Keep the map only if it wins.

## Open questions

- Does the map file get committed or stay local? Default: local (`.gitignore`), rebuilt by the hook.
- Windows: confirm `universal-ctags` installs without admin on the target machine. Ask first, per the install rule.
